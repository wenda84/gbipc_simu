# GB28181 支持 MP4（H264/H265 + AAC）发送功能设计

> 版本：2026-10-30（v4，修正 SCR/mux_rate 时序与首帧时延；基于实抓 pcap 定位）｜适用工程：gbipc_simu
> 关联文档：`Readme.md`（用户手册）、`docs/工程说明.md`（架构与打包）、`docs/GB28181_IPC模拟工具_总体方案.md`

---

## 1. 需求与目标

支持用户把**本地 MP4 文件（H264/H265 视频 + AAC 音频）**作为点播媒体源，经本工具向国标平台推送。

硬性规则（来自需求）：

- MP4 视频必须是 **H264 或 H265**；
- MP4 音频若为 **AAC**，随 PS 复用发送；
- 若音频**不是 AAC**（MP3 / AC3 / …），在日志报错，**仅发送视频**（丢弃音频）；
- 信令层、RTP 发送层**不做任何改动**，最大化复用现有链路。

设计原则：**走路线 A（ffmpeg 转封装为 MPEG-2 PS），但改为「进程内调用 ffmpeg 的 C API」而非拉起 ffmpeg 子进程。** 具体落地为：

- **不依赖本机安装 ffmpeg**：把 ffmpeg 的库文件（libav，经 PyAV 绑定）作为 wheel 解压到仓库 `libs/av/`，随工程与安装包一同发布；
- **业务代码调用 ffmpeg 的 API**（PyAV 19 的 `av.open` / `BitStreamFilterContext` / `Packet` 等 C 绑定）在进程内完成「解封装 + 比特流过滤」，再用本工程自写的 PS 封装器 `app/media/ps_muxer.py` 拼出 PS 字节流；
- GB28181 实时点播的媒体封装本来就是 MPEG-2 PS，音频复用进 PS 内部的 audio PES（`0xc0`），与现有 PS 素材（`HK264.ps` / `HK265.ps`）格式完全一致，因此下游 `PsStreamer` 零改动。

> 注：早期 v1 设计采用「拉起 ffmpeg 子进程 + `ffmpeg_path` 配置项」；因需求方要求「不依赖本机 ffmpeg、自下载内置、调用 API 而非进程」，已重构为本文档描述的 v2 方案。
>
> v3 变更（2026-10-30）：真实样本 `平安城市-鼎桥版2015-08-18.mp4` 实测「画面花屏、无声」，定位到 **PES 可选头字段错位** 与 **超大 PES 跨 pack 续发** 两个封装层根因并修复，详见 §3.6。

## 2. 方案概述

### 2.1 为什么信令层不用动

`docs/工程说明.md §1.1` 已说明本工程采用「信令优先」架构：`gbsdp.build_answer()` 实时点播只发一条 `m=video ... PS/90000` 的 SDP，**音频是复用在 PS 内部、而非独立 `m=audio` 行**。`PsStreamer` 直接吃原始 PS 字节流（按 PS pack 头 `0x000001ba` 切分、识别 `0xe0` 视频 PES 与 `0xc0` 音频 PES、按 PTS 流控、RTP 打包）。

因此「MP4 → PS 打包」这一步的产出只要符合既有 PS 格式，下游 SDP / RTP 全部零改动。缺口**只有**「MP4 → PS 字节流」，且落在 `PsStreamer` 之前。

### 2.2 数据流

```
用户选择 .mp4
      │
      ▼
device._start_stream
      │  prepare_media_source(cfg.ps_file_abs(), self._log)
      ▼
mp4_source.prepare_media_source
      ├─ .ps 源            → 原样返回 (path, is_temp=False)
      └─ .mp4/.m4v/.mov 源 → 内置 libav 解封装 + 自写 PS 封装 → 临时 PS 文件 (path, is_temp=True)
      │
      ▼
PsStreamer.start_file(ps_path)   ← 复用既有 PS→RTP 链路（UDP / TCP、PTS 流控、循环）
      │
      ▼
停止 / BYE → device._stop_stream → 删除临时 PS 文件
```

## 3. 实现要点

### 3.1 新增模块 `app/media/mp4_source.py`（libav API 版）

职责：内置 libav 加载、编码探测、解封装 + 比特流过滤、调用 PS 封装、产物校验、来源路由。

关键函数：

| 函数 | 作用 |
|---|---|
| `_load_av()` | 加载内置 libav 绑定 PyAV：先 `import av`，失败再回退到仓库内置 `libs/av`（源码态=工程根/libs/av；打包态=`sys._MEIPASS/libs/av`）。找不到返回 `None` |
| `probe_streams(src)` | 用 `av.open` 解封装，读取各流 `codec.name`，得到 `MediaProbe(video, audio)` |
| `_iter_ps_frames(av, src, do_audio)` | 解封装并逐包产出 PS 帧字典 `{stream_id, payload, pts, dts}`：视频经 `h264_mp4toannexb` / `hevc_mp4toannexb` 比特流过滤得到 AnnexB（国标 PS 需要 start code），**每个 IDR 前若缺 SPS/PPS(VPS) 则自动补齐**；AAC 帧**逐帧加 7 字节 ADTS 头**后透传（国标 PS 的 AAC 必须是 ADTS） |
| `convert_mp4_to_ps(src, on_log)` | 探测 → 按规则处理音视频 → 构造 PSM 前导包 → 调 `ps_muxer.write_ps_from_frames` 写出临时 PS，并做产物校验 |
| `prepare_media_source(src, on_log)` | 对外入口：`.ps` 直通、`.mp4/.m4v/.mov` 转封装、其它扩展名抛 `Mp4SourceError` |

编码处理规则：

- 视频 `not in {h264, hevc, h265}` → 抛 `Mp4SourceError`（无法以 PS 封装，拒绝发送）；
- 视频为 `h264` → 比特流过滤 `h264_mp4toannexb`；`hevc/h265` → `hevc_mp4toannexb`（MP4 中的 AVCC 长度前缀 → AnnexB 起始码，GB28181 PS 要求）；
- 音频 `None` → 仅视频；音频 `== aac` → 随 PS 复用（写入 `0xc0` audio PES）；音频为其它 → `on_log` 报错并丢弃音频，仅发视频。

进程内转封装管线（替代 ffmpeg CLI）：

```
av.open(src)                         # libav 解封装 MP4
  └─ ic.demux()                      # 逐包读取
       ├─ 视频包 → BitStreamFilterContext(mp4toannexb).filter(pkt) → AnnexB NAL 字节
       └─ 音频包(AAC) → 裸 AAC 帧字节
            ↓
ps_muxer.write_ps_from_frames(        # 本工程自写 MPEG-2 PS 封装器
    out, frames,
    preamble=_build_psm_pack(es_entries))   # 关键：写入 Program Stream Map
```

- **不再使用 ffmpeg 的 MPEG-PS muxer**，而是自写纯 Python PS 封装（`app/media/ps_muxer.py`），原因见 §4「AAC 识别」行：自写 muxer 配合 PSM 才能保证平台侧把 `0xc0` 正确识别为 AAC。
- 产物为临时文件（`tempfile.mkstemp`，前缀 `gbipc_`），调用方负责删除。

产物校验（`convert_mp4_to_ps` 末尾）：

- 必须含视频 PES `0x000001e0`，否则视为转封装异常并清理；
- 若声明 AAC 却检测不到 `0x000001c0` 音频 PES，打**警告**日志（提示平台可能无法解码音频，需联调确认）。

### 3.2 `app/core/device.py` 接入（与 v1 一致）

- `CallContext.media_temp_path: Optional[str]`（默认 `None`）：记录 MP4 转封装产生的临时 PS 路径（`.ps` 源为 `None`）；
- `_start_stream`：在创建 `PsStreamer` 之前调用 `prepare_media_source(cfg.ps_file_abs(), self._log)`；
  - 失败（`Mp4SourceError`，如 libav 缺失 / 编码不支持）→ 记日志并 `hangup_call`，不让呼叫卡在 CONFIRMED 无流；
  - 成功 → 用返回的 `ps_path` 喂 `PsStreamer.start_file`，并把 `is_temp` 记到 `ctx.media_temp_path`；
- `_stop_stream`：推流停止后删除 `media_temp_path` 临时文件（含停止时已经在途的呼叫，走 `_teardown` 的 drain → DISCONNECTED → `_stop_stream` 同样清理）。

### 3.3 `app/core/config.py`

- **移除了 v1 的 `ffmpeg_path` 字段**：因为不再需要外部 ffmpeg，MP4→PS 改由仓库内置的 libav 在进程内完成，无需配置 ffmpeg 路径；
- 原 `[media]` 段保留，注释说明「MP4 转封装使用内置 ffmpeg(libav)，无需 ffmpeg_path」。

### 3.4 `app/ui/settings_page.py`

- 「媒体文件」行的文件对话框过滤改为 `媒体文件 (*.ps *.mp4 *.m4v *.mov);;PS 流 (*.ps);;MP4 (*.mp4);;所有文件 (*)`；
- 提示文案更新为：「支持 .ps 素材与 .mp4（H264/H265+AAC）源；MP4 将经内置 ffmpeg 库(libav) 转封装为 PS 发送，非 AAC 音频会被丢弃。」

### 3.5 内置 ffmpeg(libav) 的获取与打包

为满足「自下载 ffmpeg 并内置仓库、业务调用其 API」：

1. **获取**：下载 PyAV 的 Windows 二进制 wheel
   `av-19.0.2-cp312-abi3-win_amd64.whl`（`python -m pip download av --platform win_amd64 --python-version 312 --only-binary=:all:`），
   解压后取其中的 `av/`、`av.libs/`（ffmpeg 的 `avcodec/avformat/avutil/swresample/...dll`）、`av-*.dist-info/` 三件套放入仓库 `libs/av/`。
2. **运行期加载**：`mp4_source._load_av()` 把 `libs/av` 注入 `sys.path`，`import av` 即加载内置副本；`av/__init__.py` 内的 delvewheel 补丁会把兄弟目录 `av.libs/` 加入 DLL 搜索路径，从而正确加载 libav。
3. **打包**：`tools/build_param/build_exe.spec` 把整个 `libs/av` 树作为数据文件打进包体（落点 `_internal/libs/av`，保持 `av/` 与 `av.libs/` 的兄弟布局）；并把 `av` 显式加入 `excludes`，避免构建机若装了 PyAV 时被 PyInstaller 从 site-packages 收集（版本不一致）。打包态下 `_load_av()` 改从 `sys._MEIPASS/libs/av` 注入。

> 体积权衡：内置 libav 会带来约 60~70MB 的 DLL（含编码器/解码器/滤镜）。当前为「稳妥优先」全量内置；若安装包体积敏感，可后续裁剪 `av.libs/` 中未用到的库（如 `avdevice/avfilter/libvmaf/libSvtAv1Enc/libvpx/libwebp/libdav1d/libopus` 等，仅保留 `avcodec/avformat/avutil/swresample/swscale` + MinGW 运行库），裁剪后需在真实平台联调验证导入与解封装正常。

> 版本管理：`libs/av` **直接以普通 git 对象入库**（不启用 Git LFS）。总量约 68MB、单文件最大 19.6MB（`avcodec-*.dll`），低于 GitHub 单文件 50MB 警告线；依赖静态、极少变更，直接入库可让 clone 零前置依赖（无需安装 git-lfs、不消耗 LFS 月度带宽额度）。代价是该 68MB 永久留在 git 历史中：后续若升级 PyAV，新版本会再叠加一份体积，届时可用 `git lfs migrate` 或重写历史迁移。

### 3.6 封装层根因修正（v3，花屏 / 无声）

真实样本实测「花屏 + 无声」，用内置 libav 做代理验证逐字节定位到两颗根因，均在自写 PS 封装层：

**根因 1：PES 可选头字段错位（→ 花屏、无声、流发现不完整）**

v2 写成 `[0xA0, flags]`，即把 `PTS_DTS_flags` 放在了第 1 字节、把 `PES_header_data_length` 位置留给了 flags。ISO 13818-1 的正确布局是：

| 字节 | 内容 | 合法值 |
|---|---|---|
| `PES[6]` | `'10'` + scrambling(2) + priority + align + copyright + original | `0x80` |
| `PES[7]` | `PTS_DTS_flags(2)` + ESCR/ES_rate/... 标志(6) | `0x80`（仅 PTS）/ `0xC0`（PTS+DTS）/ `0x00` |
| `PES[8]` | `PES_header_data_length` | `5` / `10` / `0` |
| `PES[9..13]` | 33-bit PTS（PTS+DTS 时 DTS 紧随其后 5 字节） | — |

错位后果：解封装器把**首个 PTS 字节当成可选头长度**（实测解析出 33），载荷起点整体偏移 → 视频 NAL 流错位（花屏）、音频 PES 无有效 PTS（无声），且解封装在读第一个 pack 后就报错，导致 `av.open` 只能发现视频流。`PsStreamer._parse_pts` 同步改为按 `data[7]` 取 flags、`data[9:14]` 取 PTS。

**根因 2：超大 PES 跨多个 pack 续发（→ 大片丢帧）**

v2 对 >65535 字节的访问单元写 `PES_packet_length = 0`（不限长）并按 2028 字节切到多个 pack 续发。实测 libav 的 mpegps 解封装器**不支持跨 pack 的 PES**：要么报 `Invalid data`（PES 有长度时），要么在下一个 pack 头处静默截断（`length=0` 时）。真实样本 276MB 视频因此只解出 199MB、8716/9164 包，解码仅 7424/9164 帧 —— 平台侧表现为大面积花屏/卡顿。

修正：**一帧载荷切成多个 PES，每个 PES 完整落在一个 2048 字节 pack 内，且始终写正确的 `PES_packet_length`**（与 ffmpeg 自身 PS muxer 的做法一致）：

- 首包带 PTS（有 B 帧时带 PTS+DTS），后续包不带时间戳；解码器按基本流顺序拼接（标准允许一个访问单元跨多个 PES）；
- 每包可用载荷 `= PAYLOAD_CAP(2034) − 6(PES 头) − 可选头(3/8/13)`；
- pack 不带填充，`pack = 14B pack 头 + 1 个 PES`，`pack_len ≤ 2048`；
- `PsStreamer` 侧无需改动：帧边界仍由「下一个带 PTS 的 pack」判定，RTP marker 落在帧尾 pack。

**其余同步修正**

- PSM 第二字节由 `0xC0` 改为 `0xFF`（`reserved(7)=1111111` + `marker_bit=1`），符合规范；
- 无时间戳的 PES 也写出最短可选头 `80 00 00`，不再省略可选头；
- 每帧 AAC 已加 ADTS 头（v2 后期修正），PSM 声明 `0xc0 → 0x0F(AAC)`。

**验证结果（真实样本 `平安城市-鼎桥版2015-08-18.mp4`，366.56s，H264+AAC）**

| 指标 | 源 MP4 | 转出 PS（libav 回解） |
|---|---|---|
| 视频包/帧 | 9164 | 9165（解码 9164 帧，0 错误） |
| 音频包 | 15787 | 15787（1.6M 样本 ≈ 366.5s） |
| 视频载荷字节 | 267,966,604（AVCC） | 267,908,332（AnnexB） |
| 流识别 | video/h264、audio/aac | video/h264、audio/aac（含 PSM） |

另做 RTP 回环验证（`PsStreamer` UDP 发送 → 本地收包去 RTP 头重组）：重组字节与源 PS **完全一致**，回解出 h264+aac、0 解码错误。

## 4. 抓包定位：平台侧「播约十秒停止」与「首帧慢」

样本：`temp/call.pcapng`（在 IPC 侧 172.220.0.85 抓包，含平台 172.220.0.178 转发的两路呼叫）。
媒体方向：本端 49751 → 平台 21006（`m=video ... TCP/RTP/AVP 96`，PS 经 RFC4571 封帧）。

### 4.1 抓包事实（不代表结论，均为可复算数据）

| 观测 | 数值 |
|---|---|
| 呼叫建立 | 平台 INVITE @1.366s → 本端 200 OK @1.367s（0.4ms，信令侧正常） |
| **首个 RTP 包** | **@4.392s**（距 ACK 约 **3.0s**，期间无任何媒体） |
| 媒体持续 | 4.392s → 17.561s（BYE 时刻），**没有提前停发** |
| RTP | 9902 包，PT=96，SSRC=0x12，**序列号 0 缺口**，窗口充足（客户端 wscale 7 ≈ 283KB，未出现 0 窗口） |
| 重组后 PS | 5361 pack / 894 帧（视频 326、音频 568），libav 完整解封装并解码 **0 错误** |
| PS 结构 | 全部单 pack 单 PES、无 `length=0`、单 pack ≤2048，**无结构违规** |
| 视频 PTS | 0 → 12.96s，GOP 0/2.4/3.68/4.8/6.24/8.2/10.36…（不规则，非固定 10s） |
| **pack 头 SCR** | 0 → **10719 tick = 0.119s**（而 PTS 走了 13.17s，**差 110 倍**） |
| **program_mux_rate** | 固定 **2000000**（= 100 MB/s），实际码率约 0.75 MB/s |
| SDP 端口 | 本端 200 OK 通告 `m=video 15088`，但实际 TCP 源端口 **49751**（不一致） |

结论分界：**媒体本身完整可解码**，问题出在「封装时序字段」与「首包时机」，不在丢包/停发。

### 4.2 根因与修正

1. **SCR（系统时钟参考）与 PTS 脱节（主因）**：v3 之前 SCR 用「每个 pack +1」的计数器，
   13 秒节目只前进 0.119 秒。按 ISO 13818-1 的 P-STD 模型，播放器用 SCR 恢复系统时钟来决定
   「何时该显示 PTS 为 X 的帧」：时钟几乎不动而 PTS 一路向前，等于告诉对端「还没到播放时间」，
   于是先卡住等待、缓冲耗尽后放弃 → 表现为**首帧异常慢 + 播约十秒停止**。
   修正：`scr = max(上次 SCR, DTS/PTS − 0.7s)`，单调不减、始终略早于解码时刻（同 ffmpeg PS muxer 的 max_delay 做法）。
2. **program_mux_rate 量级错误**：写死 2000000（100MB/s），与真实码率差约 100 倍，缓冲占用模型必然失真。
   修正：`mux_rate = 文件字节数 / 时长 × 1.3 / 50`（样本得 19438 ≈ 0.97MB/s）。
3. **首帧慢：点播时才做整文件转封装**。实测 274MB 样本转封装耗时 **2.47s**，加上读入 PS、
   连接 TCP，正好对应抓包里 ACK→首包 3.0s 的空窗。修正：转封装产物按
   `(绝对路径, mtime, 大小)` 缓存（重复点播 **0.000s** 命中），并在设备启动时后台预热
   （`warm_media_cache`），首次点播也无需等待。
4. **TCP 主动模式源端口与 SDP 不符**：SDP 通告 15088，实际从 49751 发出。修正：TCP 也绑定
   `local_media_port`（被占用时回退临时端口并记日志）。
5. **视频帧统一写 PTS+DTS**：源含 B 帧时 PTS 在解码顺序上会回退，平台若按 PTS 单调性调度易误判；
   现每帧都带 DTS（单调），与真实设备 PS 一致。

### 4.3 修正后自检数据（真实 366.56s 样本）

| 项 | 修正前 | 修正后 |
|---|---|---|
| SCR 末值 / 跨度 | 0.119s | **365.85s**（= 366.55 − 0.7s 提前量） |
| mux_rate | 2000000 | **19438**（0.97MB/s） |
| pack 总数结构校验 | — | 152874 pack，SCR 单调、长度字段全部有效、尾部 0 字节遗留 |
| libav 解码 | — | 9163/9164 帧、15787 音频包、**0 错误** |
| 重复点播准备耗时 | 2.47s | **0.000s**（缓存命中） |

> 待平台复测：以上修正必须在真实客户端再抓一次包确认（重点看「首包时间」与「播到 10s 之后是否仍连续」）。

## 5. 关键决策与风险

| 项 | 决策 / 结论 | 风险与缓解 |
|---|---|---|
| 复用 PsStreamer | 是，PS 字节流直接喂入 | 低；PS 格式需与 `HK264.ps` 一致 |
| 自写 PS 封装 + PSM | **关键决策**：自写 `ps_muxer` 并写入 Program Stream Map（`0xbc`），明确声明 `0xe0→H264/H265`、`0xc0→AAC` | 中→低；若缺 PSM，ffmpeg/libav 等解封装会把 `0xc0` 误判为 mp2，平台无法解码音频；已写入 PSM 并加产物校验 |
| AAC 识别 | 经 PSM 声明后，libav 能正确把 `0xc0` 解码为 `aac`（已单测验证） | 低；已加产物校验 + 缺失告警 |
| PES 可选头布局 | 严格按 ISO 13818-1：`80` / `80|C0` / `05|0A` + 33-bit PTS/DTS（见 §3.6） | 曾因错位导致花屏/无声；现有结构断言锁死 |
| 大帧封装 | 一帧切成多个「单 pack 内」PES，长度字段始终有效；不使用 `length=0` 跨 pack | 曾因 libav 不支持跨 pack PES 丢 70MB 数据；现有断言 + 真实样本回归 |
| 不依赖本机 ffmpeg | 内置 `libs/av`（PyAV wheel 自带 libav*.dll），进程内调 API | 低；构建需把 `libs/av` 一并打包（见 §3.5） |
| 进程内调 API 而非子进程 | 满足需求；无进程拉起开销、无 ffmpeg CLI 版本差异 | 低；依赖 PyAV 19 的 API 形态（如 `pkt.buffer_ptr` 取字节） |
| 非 AAC 音频 | 按需求丢弃，仅发视频，日志报错 | 已实现 |
| 视频非 264/265 | 拒绝发送并日志报错 | 已实现 |
| HEVC/H265 | `hevc_mp4toannexb` + 自写 PS 封装；`HK265.ps` 已验证 H265 可行 | 低 |
| 循环播放 | 临时 PS 文件物化到磁盘，直接复用 `PsStreamer` 的 `loop_play` 逻辑 | 低 |

## 6. 测试计划

### 6.1 单元测试（已落地，`tests/test_mp4_source.py`）

测试运行环境：venv 未安装 PyAV，`_load_av()` 自动回退到仓库内置 `libs/av` 注入，因此本测试**实际验证了内置 libav 管线**（不再是纯正则解析）。

- `test_ps_contains`：字节序列扫描工具；
- `test_prepare_routing_unsupported_ext`：不支持扩展名报错；
- `test_prepare_ps_passthrough`：`.ps` 直通返回 `is_temp=False`；
- `test_ps_pack_and_pes_layout`：**封装结构回归**——逐 pack 断言「pack 头后紧跟一个 PES 起始码、`PES_packet_length` 有效（不允许 0）、可选头 `80`/`80|C0`/`05|0A` 合法、单 pack ≤2048」，并校验 `_parse_pts` 与 `_build_pes` 的 PTS 往返一致；
- `test_mp4_to_ps_h264_aac_roundtrip`：H264+AAC MP4 转封装为 PS，验证产物含 PSM（`0x000001bc`）且其内容能被 libav 反解封装为 `h264` / `aac`；
- `test_ps_scr_tracks_pts`：**时序回归**——逐 pack 断言 `SCR` 单调不减、跨度与媒体时间轴同量级、`program_mux_rate` 与声明一致（防「播十秒停止」复发）；
- `test_prepare_media_cache_hit`：同一 MP4 重复点播命中转封装缓存（首帧不再等整文件转换）；
- `test_mp4_to_ps_video_only`：无音频轨 → 仅视频；
- `test_mp4_to_ps_non_aac_audio_dropped`：非 AAC 音频 → 丢弃音频、仅视频、日志报错；
- `test_mp4_unsupported_video_rejected`：视频非 264/265 → 拒绝发送。

运行：`runtime\venv312\Scripts\python.exe tests/test_mp4_source.py`（10 项断言，已全部通过）。

### 6.2 端到端联调（用内置 libav，无需本机 ffmpeg）

1. 用 `build.bat` 构建安装包（会自动把 `libs/av` 打进 `_internal/`）；
2. 准备一个 H264+AAC 的 MP4，配置 `ps_file` 指向它，「启动」并让平台点播，确认出图**且出声**；
3. 准备一个 H264+MP3 的 MP4，确认日志出现「非 AAC…仅发送视频」报错，**仅出图**；
4. 准备一个 VP9 / MPEG4 等非 264/265 的 MP4，确认日志出现编码不支持报错且设备挂断、不卡流；
5. 循环播放、TCP/UDP 两种媒体传输各测一遍；
6. 停止设备，确认缓存 PS 在进程退出时被清理（无残留）；
7. 重复点播同一 MP4，确认日志出现「命中转封装缓存」且首包时延 < 1s；
8. 用 `Wireshark` 复核 PS：pack 头 SCR 应随时间线性增长、`mux_rate` 与码率同量级。

### 6.3 平台联调验证清单

- [ ] PS 中音频 PES 为 `0xc0`，且有 PSM（`0xbc`）声明其为 AAC；
- [ ] AAC 在平台侧能解码出声（PSM 已声明，较 v1 更可靠）；
- [ ] 用真实样本 `平安城市-鼎桥版2015-08-18.mp4`（366s，大 I 帧）点播，画面无花屏、无卡顿、有声；
- [ ] H265 MP4 出图正常；
- [ ] 平台侧连续播放 ≥ 60s 不中断（重点验证「播约十秒停止」已消除）；
- [ ] 点播到出首帧 < 1.5s（缓存预热生效）；
- [ ] 老平台（海康/宇视）对 PS 细节（pack 头 / system header / 单 pack 单 PES）不挑剔；
- [ ] 多台/多次点播无临时文件泄漏；
- [ ] 安装包 `dist/.../_internal/libs/av/av.libs/` 下 libav*.dll 存在，缺 ffmpeg 的干净机器上也能出图出声。

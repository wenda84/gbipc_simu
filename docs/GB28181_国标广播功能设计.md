> 版本：v1.0（设计稿）  
> 依据：GB/T 28181-2016（9.12.1、A.2.5 d、A.2.6 l、C.2.4、附录 D.1 / F / K / L / M）  
> 适用工程：gbipc_simu 工程根目录（本文档所在项目的根目录）  
> 关联文档：《GB28181_IPC模拟工具_总体方案.md》《工程说明.md》

## 0. 结论摘要

1. **本工具在语音广播流程中的角色是「语音流接收者」**（即语音输出设备，类型编码 **137**），不是发送者。设备收到平台的广播通知后，**主动向语音流发送者发起 INVITE（UAC）**，接收平台媒体服务器下发的 **PCMA（G.711A，PT=8，8 kHz，单声道）** 音频流并本地播放。
2. 本工程原有实现**只具备 UAS 能力**（应答 INVITE）。国标广播的关键增量是**新增 UAC 出呼能力**（`makeCall` + 自定义 SDP 注入 + Subject 头域）。
3. 自定义 SDP 注入机制在 UAC 路径**可用**：本工程对 pjproject 的补丁位于 `pjsua_process_msg_data()`，该函数在 `invite_session()`（`pjsua_call.c:564`）中对外发 INVITE 调用，因此 `txOption.msgBody` 注入自定义 SDP 对出呼同样生效（已核对源码）。
4. **【已实证并修复的关键阻塞】UAC 侧的 ENOMEDIA 容忍缺口**：pjsua 在 UAC 收到 200 OK 时，媒体更新发生在 invite 状态为 `CONNECTING` 的时刻，会命中 `pjsua_call.c:5343` 的拆链条件而被以 **415（SDP negotiation failed）** 拆链——原有 ENOMEDIA 容忍补丁（`pjsua_call.c:5408`）位于该判断之后的成功分支，**覆盖不到 UAC 路径**（UAS 路径因状态为 `EARLY` 而幸免）。已在该失败分支内新增 ENOMEDIA 放行（同为 `PJSUA_CALL_NO_MEDIA_DEFAULT` 守护），并重编译 pjsua2 验证通过。详见 §10.1。
5. 延续「信令优先（signaling-only）」架构：pjsua2 只做 SIP 信令，**音频 RTP 接收、PCMA 解码、播放、电平计算全部由 `media/` 层自理**，不启用 pjsua 的媒体通道。
6. 音频播放后端采用 **`sounddevice`（RawOutputStream，自带 PortAudio）**；UI 只呈现分段 LED 音量表，**不显示 dBFS 数值**。

### 1.2 范围界定

**本期实现**

- 语音广播通知（`Notify/Broadcast`）接收与应答（`Response/Broadcast`）。
- 作为语音流接收者发起 INVITE（UAC），`s=Play` + `m=audio`，仅 PCMA。
- PCMA RTP 接收、抖动缓冲、丢包补偿、A 律解码。
- 本地音频播放 + 实时电平指示。
- 设备目录中上报 137 语音输出通道（勾选后）。
- 广播会话的启停、异常收敛、与既有「实时点播推流」并行不互斥。

**明确不做**

| 项 | 说明 |
|---|---|
| 语音对讲（`s=Talk`） | 标准中 `s=Talk` 表示语音对讲（附录 F），与广播是不同流程；本期收到仍回 `488` |
| 其他音频编码 | G.723.1 / G.729 / G.722.1 / SVAC 均不支持，Offer 只回 PCMA |
| 音频采集与上行 | 本工具是接收者，不采集麦克风、不发送音频 |
| 多路并发广播 | 同一时刻仅维持一路广播会话（重复通知则释放旧链路） |
| 语音输出通道的订阅通知 | 仅实现目录（Catalog）查询应答中的上报 |

### 1.3 对既有文档的一处更正

`Readme.md` 第 289 行表述为「语音广播（`s=Talk`）」。按 GB/T 28181-2016 附录 F，`s=Talk` 表示**语音对讲**；**语音广播的 INVITE 使用 `s=Play` + `m=audio`**（9.12.1.2 步骤 e / f：`s` 字段为 "Play"，`m` 字段媒体参数标识为 "audio"）。本设计实现后应同步修正该处表述。

## 2. 国标流程梳理

### 2.1 角色与编码

| 角色 | 本工具中的实体 | 编码 |
|---|---|---|
| 语音流发送者 | 中心侧的语音输入设备 / 媒体服务器（外部） | 类型编码 **136**（语音输入设备） |
| SIP 服务器（平台） | `server_id` / `server_domain` | 类型编码 200 段 |
| **语音流接收者** | **本工具（IPC 模拟器）** | 主设备 IPC（131/132）+ 语音输出通道 **137** |

依据 9.12.1.1：设备若具备语音输出能力，**必须在设备目录查询/订阅时上报语音输出设备**（否则视为不具备该能力）；上报的语音输出设备 ID **类型编码为 137，其 ParentID 填写其父设备（本 IPC）的 ID**。

9.12.1.1 同时明确：平台既可直接对 137 语音输出设备发广播通知，**也可直接对 IPC 主设备编码发通知**，表示对该 IPC 接入的所有语音输出设备广播。因此设备侧必须**同时接受 TargetID = 主设备 ID 与 TargetID = 137 通道 ID** 两种寻址。

### 2.2 命令流程（9.12.1.2 图 27，仅列设备侧信令）

| 序号 | 方向 | 消息 | 关键内容 |
|---|---|---|---|
| 1 | 平台 → 设备 | `MESSAGE` (MANSCDP `Notify/Broadcast`) | `To` = 语音流接收者 ID；体含 `SourceID`（语音输入设备 ID）、`TargetID`（语音输出设备 ID） |
| 2 | 设备 → 平台 | `200 OK` | 无体；**由本工程 SIP 适配层自动应答** |
| 3 | 设备 → 平台 | `MESSAGE` (MANSCDP `Response/Broadcast`) | `To` = SIP 服务器 ID；体含 `DeviceID`、`Result` |
| 4 | 平台 → 设备 | `200 OK` | 事务完成 |
| 5 | 设备 → 平台 | **`INVITE`（设备作 UAC）** | `To` = 语音流发送者 ID；`Subject` 标识媒体链路；SDP `s=Play`、`m=audio`、`a=recvonly` |
| 6–16 | 平台内部 | 3PCC / B2BUA | 平台与媒体服务器、语音流发送者建链，**设备不参与** |
| 17 | 平台 → 设备 | `BYE` | 中断广播 |
| 18 | 设备 → 平台 | `200 OK` | 停止接收、停止播放、复位音量表 |

> 信令 6–16 由平台通过 B2BUA 代理 + 三方呼叫控制完成。设备侧只需完成 1–5 与 17–18，并在收到 `200 OK`（信令 14 转发）后从 `200 OK` 的 SDP 中获知媒体服务器的**媒体接收/发送地址、端口、PCMA 载荷与 SSRC**。

### 2.3 MANSCDP 报文（A.2.5 d / A.2.6 l）

**广播通知（平台 → 设备）**

```xml
<?xml version="1.0" encoding="GB2312"?>
<Notify>
  <CmdType>Broadcast</CmdType>
  <SN>992</SN>
  <SourceID>31010400001360000001</SourceID>
  <TargetID>31010403001370002272</TargetID>
</Notify>
```

**广播应答（设备 → 平台）**

```xml
<?xml version="1.0" encoding="GB2312"?>
<Response>
  <CmdType>Broadcast</CmdType>
  <SN>992</SN>
  <DeviceID>31010403001370002272</DeviceID>
  <Result>OK</Result>
</Response>
```

要点：

- `Content-Type: Application/MANSCDP+xml`（本工程 `manscdp.CONTENT_TYPE` 已一致）。
- **SN 必须回显**请求中的 SN（A.1：响应命令中的 SN 应使用请求命令中的 SN）。
- 应答的 `DeviceID` 为**语音输出设备的设备编码**；实现上取通知中的 `TargetID` 回显，若通知寻址到主设备 ID 则回显主设备 ID，二者皆与标准语义一致。
- 通知报文**不含 `DeviceID` 元素**，`SourceID`/`TargetID` 需从其他子元素解析（现有 `manscdp.parse()` 已把这些放入 `extra` 字典，无需改造解析器）。
- 正文按 GBK 编码；本工程 `_esc()` 已把非 ASCII 转为数字字符引用，兼容 GB2312。

### 2.4 SDP 参数（9.12.1.3.2 + 附录 F）

**对端（媒体服务器/语音流发送者）侧示例**（标准原文）：

```
v=0
o=64010600002020000001 00 IN IP4 172.20.16.3
s=Play
c=IN IP4 172.20.16.3
t=0 0
m=audio 8000 RTP/AVP 8
a=sendonly
a=rtpmap:8 PCMA/8000
y=0100000001
f=v/////a/1/8/1
```

**本设备（接收者）应构造的 Offer / Answer**：

```
v=0
o=<设备ID> 0 0 IN IP4 <本机IP>
s=Play
c=IN IP4 <本机IP>
t=0 0
m=audio <本机音频接收端口> RTP/AVP 8
a=recvonly
a=rtpmap:8 PCMA/8000
y=<本端10位SSRC>
f=v/////a/1/8/1
```

字段依据：

| 字段 | 取值 | 依据 |
|---|---|---|
| `s=` | `Play` | 附录 F：`Play` = 实时点播（广播走实时点播信令） |
| `m=` media | `audio` | 附录 F：`audio` 标识传输音频内容 |
| `m=` 端口 | 本端绑定端口 | 接收者声明自身收流端口 |
| `m=` 传输 | `RTP/AVP`（UDP，默认）；`TCP/RTP/AVP`（可选） | 附录 F |
| 方向 | `a=recvonly`（本端只收） | 对端为 `sendonly`，方向互补 |
| `rtpmap` | `8 PCMA/8000` | C.2.4 a)：PT=8、PCMA、8 kHz、单声道 |
| `y=` | 10 位十进制，首位 0（实时流） | 附录 F 注 4 + y 字段定义 |
| `f=` | `v/////a/1/8/1` | 附录 F 注 3：仅音频时视频段保留 `v/////`；`a/1/8/1` = G.711 / 64 kbps / 8 kHz |
| TCP 时 `a=setup` | 本端 `passive`（媒体接收方宜作服务端） | 附录 L |

**SSRC 处理**：附录 F 注 4 规定域内媒体的 SSRC 由本域监控系统产生并通过 INVITE 送给设备使用。广播场景中**发送方是平台媒体服务器**，因此以 **`200 OK` 中的 `y=` 为准**——接收侧用它校验入流 SSRC。本端 Offer 中的 `y=` 仅作建议值。

### 2.5 音频 RTP 封装（C.2.4）

| 参数 | 取值 |
|---|---|
| 负载类型 PT | **8** |
| 编码名称 | **PCMA**（G.711 A 律） |
| 时钟频率 | 8 kHz |
| 通道数 | 1 |
| `m` 行 media | `audio` |

- 一个 RTP 包中音频载荷应为**整数个编码帧**，时长在 **20 ms ~ 180 ms** 之间。实现按 **20 ms = 160 采样 = 160 字节载荷**处理，并兼容 40/60 ms 聚合包（按 160 字节边界切分）。
- 与视频点播的 PS/90000 封装完全不同：广播是**裸 PCMA 基本流封装**，**没有 PS 头、没有 PES**，不能复用 `PsStreamer` 的逻辑。
- RTP 头按 RFC 3550 常规解析（V/P/X/CC、M、PT、seq、timestamp、SSRC）；本场景不需要 CSRC/扩展头，但解析时按 CC 与 X 位正确跳过。

### 2.6 Subject 头域（附录 K）

格式：

```
Subject: 媒体流发送者ID:发送方媒体流序列号,媒体流接收者ID:接收方媒体流序列号
```

广播场景取值：

```
Subject: <SourceID>:0,<本设备ID>:1
```

- 发送方序列号首位取 `0`（实时媒体流），同一实时流内取值唯一；接收方序列号在同一接收者上不重复。
- 实现上序列号取进程内单调递增计数器（首位固定 `0`），便于同源重复呼叫时按附录 M 做链路清理。

### 2.7 设备目录与 137 通道（9.12.1.1 + D.1）

勾选「国标广播」后，`Catalog` 应答须在原有 IPC 目录项之外**追加一条 137 语音输出设备**：

| 字段 | 取值 |
|---|---|
| `DeviceID` | 主设备 ID 的第 11–13 位替换为 `137`（D.1：类型编码位于第 11、12、13 位） |
| `Name` | `<设备名称>-语音输出` |
| `Manufacturer` / `Model` | 同主设备 |
| `CivilCode` | 同主设备 `civil_code` |
| `ParentID` | **主设备 ID**（9.12.1.1 明确要求父设备填其所属 IPC） |
| `Parental` | `0` |
| `RegisterWay` | `1` |
| `Secrecy` | `0` |
| `Status` | `ON` |

`SumNum` 相应由 1 变为 2。未勾选时不追加该条目（对应标准「不上报语音输出设备，则表示该设备没有语音输出能力」）。

### 2.8 媒体流保活（附录 M）

- 附录 M c)：平台以 Subject 中「媒体流发送者ID:发送方媒体流序列号」标识媒体源。设备收到以同一媒体源标识的新呼叫请求时，应**释放既有链路并建立新链路**。广播侧同样适用：同一 `SourceID` 的重复通知应先释放旧广播会话。
- 附录 M b)：监测到媒体流发送方故障/离线应主动释放媒体链路。作为接收者，本设计增加**入流超时监测**：连续 `broadcast_rtp_timeout`（默认 15 s）未收到有效 RTP 包，则记录告警并主动发送 `BYE` 释放链路，避免界面长期停留在「广播中」。

### 3.3 广播子状态机

广播能力是**叠加**在既有注册状态机之上的独立子状态，二者解耦：

```
                      ┌─────────── broadcast_disabled ───────────┐
                      │  cfg.broadcast_enabled == False          │
                      │  收到 Notify/Broadcast → 回 Result=ERROR │
                      └─────────────────────────────────────────┘
                                    │ 勾选 + 启动（仅停止态可勾选）
                                    ▼
IDLE ──Notify/Broadcast──▶ ANSWERING ──(Response 已发)──▶ INVITING
                                  │                            │
                                  │                      200 OK + ACK
                                  │                            ▼
                                  │                        RECEIVING
                                  │                       （播放 + 电平）
                                  │                            │
                     BYE / 入流超时 / 停止设备 / 重复通知        │
                                  └────────────────────────────┘
                                              ▼
                                            IDLE
```

- `INVITING` 阶段若收到 `4xx/5xx/6xx` 或事务超时 → 记日志、回到 `IDLE`、UI 提示「广播建立失败」（不自动重试，避免与平台形成呼叫风暴）。
- 广播子状态变化通过新增事件 `on_broadcast_state(text)` 上报 UI。

### 3.4 线程模型

| 线程 | 归属 | 职责 |
|---|---|---|
`gb-device`（既有 worker） | core | 串行处理 SIP 事件、广播子状态机、发 MESSAGE、发起 INVITE
`pcma-recv`（新） | media | socket 收包 → RTP 解析 → A 律解码 → 入抖动缓冲
`audio-cb`（新，由播放后端驱动） | media | 出缓冲 → 播放 → 计算电平 → **限流投递** worker 队列
`ps-streamer`（既有） | media | 视频点播推流，与广播互不影响
UI 线程 | ui | 仅接收 Qt 信号更新控件

**跨线程约束（沿用既有约定）**：

1. 收流线程与播放回调**不得**直接触碰 Qt 对象，也**不得**直接调用 `DeviceEvents`；统一经 `device._queue.put(("broadcast_level", ...))` 投递，由 worker 串行调用 `out.on_broadcast_level()`。
2. 电平投递**必须限流**（默认 25 Hz，并采用「有未消费则丢弃」策略），否则 50 包/秒 × 每包一次入队会挤占 SIP 事件队列。
3. UI 复位一律走 `Signal`（既有 `tests/probe_qt_singleShot_thread.py` 已固化的结论）。

**PJSIP 实现要点**

```python
def make_call(self, to_uri: str, subject: str, sdp: str) -> int:
    if self._acc is None:
        raise RuntimeError("account not created")
    call = _Call(self, self._acc, pj.PJSUA_INVALID_ID)
    prm = pj.CallOpParam(True)          # 带默认呼叫设置
    prm.opt.audioCount = 0              # 关闭 pjsua 自带媒体（信令优先）
    prm.opt.videoCount = 0
    prm.txOption.targetUri = to_uri     # Request-URI 与 To 头域
    prm.txOption.contentType = "application/sdp"
    prm.txOption.msgBody = sdp
    hdr = pj.SipHeader()
    hdr.hName = "Subject"
    hdr.hValue = subject
    prm.txOption.headers.append(hdr)
    call.makeCall(to_uri, prm)
    cid = call.getId()
    with self._lock:
        self._calls[cid] = call
    return cid
```

**已验证的技术前提（关键）**

| 前提 | 证据 |
|---|---|
| `txOption.msgBody`（application/sdp）能覆盖外发 INVITE 的自动 SDP | `pjsua_process_msg_data()` 的补丁在 `invite_session()` → `pjsua_call.c:564` 被调用；该函数即出呼构造 INVITE 的位置 |
| 出呼路径容忍「无活跃媒体」（ENOMEDIA） | `pjsua_call.c:5408` 的补丁对**任意 INVITE 状态**把 `PJMEDIA_SDPNEG_ENOMEDIA` 归为成功 |
| 出呼 2xx 的 ACK 由 pjsua 自动维护 | pjsip invite session 标准行为，无需业务层干预 |

> **仍需早期实证（M0 探针）**：UAC 场景下 `200 OK` 携带对端 SDP 后，pjsua 的 SDP 协商/媒体更新链路是否全程落在 ENOMEDIA 容忍分支内、呼叫能稳定进入 `CONFIRMED`。UAS 路径已验证；UAC 路径建议先写最小探针（不做媒体）验证后再进入后续里程碑。

    # 4) 释放同源旧链路（附录 M c）

### 4.6 `media/pcma_receiver.py`（新）

```python
class PcmaReceiver:
    """PCMA（G.711A）RTP 接收器。UDP 直接收；TCP 按 RFC4571 解帧（本端作服务端）。"""

    def __init__(self, protocol: str, local_ip: str, local_port: int,
                 expect_ssrc: str | None = None, jitter_ms: int = 60,
                 on_frame: Callable[[bytes], None] | None = None,
                 on_log: Callable[[str], None] | None = None) -> None: ...

    def start(self) -> None: ...
    def stop(self) -> None: ...
    def is_running(self) -> bool: ...
    def stats(self) -> dict: ...   # rtp / bytes / lost / dup / out_of_order / last_rx_age
```

实现要点：

1. **端口绑定**：UDP `bind((local_ip or "0.0.0.0", local_port))`，建议设置 `SO_REUSEADDR` 并在 `stop()` 时 `shutdown` + `close` 唤醒阻塞 `recvfrom`（与 `PsStreamer.stop()` 同法）。TCP 场景按附录 L「接收方宜作服务端」`listen(local_port)`，只接受一个连接，按 2 字节大端长度前缀解帧。
2. **RTP 校验**：版本 = 2；`PT == 8`；按 `CC`/`X` 正确计算头长（含扩展头）；载荷非空。
3. **SSRC 策略**：若 Answer 给出了 `y`，则只接受该 SSRC 的包；未给出时**锁定首个合法包**的 SSRC 与源地址（防串流），并记录日志。
4. **抖动缓冲**：`deque` 按 `seq` 有序插入（`seq` 回绕用 16 位差值比较）；目标深度 `jitter_ms`；溢出（>200 ms）丢最旧追平延迟；重复包丢弃。
5. **丢包补偿**：检测 `seq` 空洞 → 用上一帧 PCM 以 0.5 增益重复填充（最多 3 帧），超出则以静音填充，并累计 `lost` 计数。
6. **载荷按帧切分**：载荷长度非 160 字节整数倍时，按 160 字节边界切分并对余数做补零（兼容 40/60 ms 聚合包）。
7. **`stop()` 幂等**，可重复调用。

**电平映射（UI 语义）**

| 步骤 | 公式 | 说明 |
|---|---|---|
| RMS | `rms = sqrt(mean(x_i^2))` | 每帧 160 采样 |
| dBFS | `20*log10(rms/32768)` | 满幅 0 dBFS，静音 → `-inf`（钳到 `-96`） |
| 归一化 | `level = clamp((dbfs + 60)/60, 0, 1)` | `-60 dBFS → 0`，`0 dBFS → 1` |
| 包络 | 快攻慢放：`cur = max(level, cur*0.75 + level*0.25)` | 避免 LED 抖动 |
| 峰值保持 | `peak = max(level, peak - 0.02)`（每帧） | 参考信号强度表的峰值跌落手感 |

class AudioSink(abc.ABC):
    """播放后端抽象：由具体后端驱动 on_pull 拉取 PCM，屏蔽设备差异。"""

    def start(self, on_pull: Callable[[int], bytes], sample_rate: int = 8000,

| 方案 | 依赖增量 | 优点 | 缺点 |
|---|---|---|---|
| **A. `sounddevice`（已采用）** | `sounddevice` + `cffi` + `pycparser`（约 1.3 MB，自带 PortAudio DLL） | `RawOutputStream` 原生支持原始 PCM 字节流；与 pull 消费模型天然契合；跨平台；实测无需 numpy | 新增 pip 依赖；打包需带上 PortAudio DLL（`_sounddevice_data/portaudio-binaries/`，待随包验证） |
| B. `PySide6-Addons`（QtMultimedia） | 约 +150 MB 安装体积 | 纯 Qt 技术栈，`QAudioSink` 低延迟、文档完善 | 分发包由约 143 MB 膨胀到 300 MB+；Qt multimedia 插件需额外打包；与「轻量测试工具」定位冲突 |
| C. `ctypes` + winmm（零依赖） | 无 | 完全无新依赖；`waveOut*` 原生流式播放；Windows 系统 DLL | 需自研约 150–250 行缓冲/回调管理；仅 Windows（本工程本即 Windows-only） |

**已定方案 A**（用户确认）。实测于本机：`sounddevice 0.5.6` + `cffi 2.1.1` 安装成功，`query_devices()` 可见 Realtek 输出设备；**未安装 numpy 亦可使用**（采用 `RawOutputStream.write(bytes)` 的写入线程模型，不用回调数组形态）。

`AudioSink` 抽象保留了切换能力，后续若需改为 B/C 只替换一个实现类。

**运行期降级**：`SoundDeviceSink` 打不开设备或在播放中设备异常（被独占/拔出）时，自动转为「按播放节拍不出声」的空播放，**收流与电平指示不中断**；`NullSink` 为显式无设备实现。`GbDevice` 另支持环境变量 `GBIPC_FORCE_NULL_SINK=1` 强制空播放，供无头环境与自动化测试使用。

### 6.2 为何不自研 PS 封装或复用 `PsStreamer`

广播是 **裸 PCMA 基本流**（C.2.4），与点播的 PS/90000 封装（C.1）在载荷、PT、时钟频率、流结构上完全不同，且方向相反（收 vs 发）。强耦合复用会污染既有稳定的推流路径，故独立实现 `PcmaReceiver`。

### 6.3 为何电平计算放在播放拉取路径

保证「有电平表即有真实解码数据」，且 `NullSink`（无音频设备的开发机/CI）下电平表仍可验证，避免把可测试性绑定到音频硬件。

### 6.4 未启用时回 `Result=ERROR` 而非静默忽略

让平台与抓包侧都能观测到设备的明确拒绝，符合 A.2.6 语义，也便于测试断言。

## 7. 异常与边界

| 场景 | 处理 |
|---|---|
| 未勾选广播收到 `Notify/Broadcast` | 回 `Response/Broadcast` + `Result=ERROR`，日志提示 |
| 收到通知但未注册在线 | 回 `Result=ERROR`，日志提示 |
| `TargetID` 既非主设备 ID 也非 137 通道 ID | 回 `Result=ERROR`（非本机目标） |
| 同源（同 `SourceID`）重复通知 | 先释放旧广播会话（`BYE` + 停收流），再建新链路（附录 M c） |
| 广播进行中又收到视频点播 INVITE | 两条链路并行：点播 = UAS 推流（`kind=play`），广播 = UAC 收流（`kind=broadcast`），互不干扰 |
| `INVITE` 被 `4xx/5xx/6xx` 拒绝或事务超时 | 记日志、回到 `IDLE`、UI 提示失败；**不自动重试** |
| `200 OK` 的 SDP 不含 `PCMA/8000` 或 PT≠8 | 视为协商失败：立即 `BYE`，告警「不支持该音频编码」 |
| 入流 RTP 的 SSRC 与协商 `y` 不一致 | 丢弃该包并计数；累计异常超阈值记告警 |
| 入流中断超过 `broadcast_rtp_timeout` | 告警 + 主动 `BYE` 释放链路，UI 由「广播中」回落 |
| 抖动缓冲溢出（对端突发） | 丢最旧包追平延迟，累计计数 |
| 播放后端初始化失败 | 自动降级 `NullSink`，收流与电平表继续工作，日志明确提示 |
| 运行中「停止设备」 | `_teardown` 中先 `BroadcastSession.stop()`（停收流/关播放）→ 再 `hangup` 广播呼叫 → 既有排空与注销流程 |
| `broadcast_media_port` 与 `local_media_port` 冲突 | `_validate()` 拦截并提示 |

## 10. 风险与对策

### 10.1 【已实证并已修复】UAC 出呼侧 ENOMEDIA 容忍缺口（415 拆链）

**现象**：设备按设计发出广播 INVITE、平台回 200 OK 后，pjsua 立即把呼叫以
**415（SDP negotiation failed）** 拆链，广播链路无法建立。

**根因**：`pjsua_call.c` 中 `pjsua_call_on_media_update()` 的失败分支：

```c
5325  if (status != PJ_SUCCESS) {                       /* ENOMEDIA 落在这里 */
5327      pjsua_perror(THIS_FILE, "SDP negotiation has failed", status);
...
5343      if ((inv->state != PJSIP_INV_STATE_NULL &&
5344          inv->state != PJSIP_INV_STATE_EARLY &&
5345          inv->state != PJSIP_INV_STATE_CONFIRMED) ||
5346          (inv->state == PJSIP_INV_STATE_EARLY && call->med_cnt == 0))
5349          call_disconnect(inv, PJSIP_SC_UNSUPPORTED_MEDIA_TYPE, &reason);   /* 415 */
```

- **UAS（实时点播应答）路径**：媒体更新发生在 `EARLY` 状态，原有 ENOMEDIA 容忍补丁
  （`pjsua_call.c:5408`）虽位于成功分支、却也足以让流程收敛，故历史测试一直通过；
- **UAC（出呼，本功能）路径**：收到 200 OK 时 invite 状态为 **`CONNECTING`**，
  既不等于 `EARLY` 也不等于 `CONFIRMED` → 条件成立 → 被 415 拆链。
  原有的 ENOMEDIA 补丁在 5353 行就已 `goto on_return`，**根本走不到**。

**修复**（沿用 `PJSUA_CALL_NO_MEDIA_DEFAULT` 守护，与既有 4 处改动同一风格，新增第 5 处）：

```c
#if defined(PJSUA_CALL_NO_MEDIA_DEFAULT) && PJSUA_CALL_NO_MEDIA_DEFAULT
        if (status == PJMEDIA_SDPNEG_ENOMEDIA) {
            goto on_return;          /* 不拆链：ENOMEDIA 是信令优先架构的预期结果 */
        }
#endif
```

**验证**：重编译 pjsua2（`tools/build_param/build_pjsua_win.sh`）后，
广播链路稳定进入 `CONFIRMED`；BYE 收到 `200 Normal call clearing`。
`tests/selftest_full.py`（点播 TCP/UDP）与 `tests/gui_selftest.py`（10 项断言）
全部回归通过，UAS 路径无副作用。

**影响面核查**：`med_update_success` 在该失败分支保持 `PJ_FALSE`，其唯一消费点
（`pjsua_call.c:6475/6491`）仅用于回滚「临时媒体」，本架构无临时媒体，故无副作用。
日志中仍会打印一条 `SDP negotiation has failed: ... ENOMEDIA` —— 属预期噪声，非错误。

### 10.2 风险与对策汇总

| 风险 | 等级 | 对策 |
|---|---|---|
| UAC 出呼在 `200 OK` 后 SDP 协商被 415 拆链 | ~~中~~ **已发生并已修复** | 见 §10.1：在失败分支新增 ENOMEDIA 放行（第 5 处守护补丁）+ 重编译验证 |
| 音频播放后端引入新依赖/打包风险 | 中 | `AudioSink` 抽象 + 自动降级；**待办**：跑 `tools/build_param/postbuild_smoke.py` 验证打包后 PortAudio DLL 可加载 |

| 无音频设备的开发机无法验收「可听到声音」 | 低 | `NullSink`（或 `GBIPC_FORCE_NULL_SINK=1`）+ WAV 落盘 + 电平曲线作为可验收的客观证据链 |
